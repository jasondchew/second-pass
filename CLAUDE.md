# Project Context

**Second Pass** — small, deliberately minimal Streamlit tool supporting Jason's general study and learning habit. It is a general-purpose study tool that works for any topic he's curious about; it is not tied to any one subject, course, or employer. Named 2026-08-26 after the "second pass" study technique (first pass = read/watch, second pass = write it out from memory) — confirmed clear of any real naming collision in this space. It is NOT an AI note-taker and does not transcribe live conversations. It supports one specific gap in the workflow: turning a handwritten (or tablet-sketched) study summary into an organized, searchable reference entry.

**Note:** the folder was renamed to `Second Pass` (and the log file to `second_pass.md`) by Jason himself 2026-08-26, after repeated automated rename attempts hit a Windows file lock (likely OneDrive syncing the `.venv`). `app.py`'s `LOG_PATH` was updated to match. The log file was renamed again, to `study_log.md`, on 2026-09-05 (app folder itself stays `Second Pass`) — `LOG_PATH` updated to match again.

# The workflow this tool supports

1. Jason reads/watches something about whatever he's currently curious about.
2. He types the topic/material into the app and gets exactly 2 retrieval-practice prompts back (lowered from 3-4 on 2026-09-23 at his request: the generated questions were too much of a cognitive reach and made studying feel like a chore; the prompts are now one plain recall question plus one small step past recall ("why does this matter / how does it work"), deliberately not deep conceptual, multi-part, compare-contrast, or new-scenario questions. He first got 2 pure-recall questions, then asked for slightly deeper than that "but don't push it").
3. He goes away from the screen and answers them from memory — handwritten on paper, sketched on an iPad (Notability/GoodNotes etc.), or typed directly. Handwriting/sketching is encouraged as the stronger retrieval-practice step, but typing is a first-class option, not a fallback — this tool doesn't gate on how the answer was produced.
4. He brings the summary back by typing straight into the answer box, or by uploading a photo/PDF export of a handwritten/sketched page — the app transcribes uploads via Claude's vision (`LogLLM.transcribe`) into that same box, and he reviews/edits before saving.
5. The app classifies the entry into a subject (reusing an existing one from the log when it fits, rather than creating near-duplicates), tags a content type only when one genuinely applies (e.g. "BRD", "Recipe", "Proof"), and appends a clean entry to `study_log.md`.
5b. **Verify-before-write (added 2026-09-21):** Jason asked that the log only receive notes that have been checked for accuracy. `verify_and_correct()` in `app.py` now runs BEFORE anything is written: the organized/merged bullets go through `check_understanding_prompt`; if it flags anything, `revise_entry_prompt` fixes just those points and it re-checks, up to 2 revisions. Only the final bullets are written (`append_entry` or `replace_entry`). This supersedes the older "save his own words even when wrong" behavior described in step 7. Cost: 1 extra check call per save, plus revise+recheck only when flagged. Honest limit: "verified" means AI-checked against the material/model knowledge, not a guarantee; the UI labels it that way, and the manual "Revise flagged answers" button remains for anything still flagged after 2 passes.
6. The result of that final check (previously a separate post-save call, added 2026-08-26 after Jason pointed out the tool captured his answers but never told him whether they were correct) call compares what he wrote against the original material/prompts and surfaces what it confirms vs. flags as possibly wrong or incomplete (`check_understanding_prompt`) — added 2026-08-26 after Jason pointed out the tool captured his answers but never told him whether they were actually correct. Labeled as AI-generated so he double-checks anything surprising rather than trusting it blindly.
7. If the check raises flags, a "Revise flagged answers" button (added 2026-09-05) calls `revise_entry_prompt` to rewrite only what was flagged (leaving everything else in his own words untouched), overwrites the just-saved entry in `study_log.md` in place via `replace_entry()` (matches on the exact previously-appended entry text, swaps in the new bullets under the same title/tag/date line), then re-runs the Quick Check against the revised bullets. This can be clicked repeatedly — each pass targets whatever's still flagged — until a check comes back clean, so the log entry itself, not just his live answer, converges on something accurate. Unlike the original save (which intentionally preserves his own words as the archived record even when wrong), this revise path DOES edit the saved entry — that's the point of it existing.

# In-progress draft persistence (added 2026-09-05)

Jason asked what happens if he closes the tab mid-answer and wanted that to survive. `st.session_state` alone doesn't survive a closed tab or full page reload, so both text areas (`material_box`, `answer_box` — keyed widgets, not plain `value=` params anymore) now autosave to `.second_pass_draft.json` (gitignored — personal in-progress scratch, not the system of record) via an `on_change` callback (`persist_draft()`), which fires when a box loses focus after an edit. On app load, if that file exists, its contents repopulate `material_box`, `prompts`, and `answer_box` before the widgets render, and a one-time `st.info` banner confirms the restore. The draft is deleted (`clear_draft()`) the moment "Organize & save to study log" succeeds, so a completed round doesn't get mistaken for an unfinished one on the next launch.

**Known limitation, told to Jason directly:** `on_change` only fires on blur (clicking/tabbing away from the box), not per-keystroke. If he closes the tab immediately after typing without ever clicking elsewhere first, whatever's typed since the last blur can still be lost. This is an accepted tradeoff for staying in native Streamlit widget behavior rather than adding JS-level autosave.

# Enrich-not-duplicate on repeated sessions (added 2026-09-05)

Jason asked: if he continues a previous session with identical Section 1 notes, don't write a redundant new log entry - enrich the existing one instead. Implementation: `.study_log_index.json` (gitignored, mechanical bookkeeping, not real content like `study_log.md`) maps a SHA-256 hash of the exact (stripped) Section 1 notes text (`material_key()`) to the entry it produced (`subject`/`tag`/`title`/`bullets`/`entry_text`). On save, `find_prior_entry()` looks up that hash; if found AND its `entry_text` still appears verbatim in the current log (guards against stale entries from manual edits), the save takes the enrich path instead of the normal one: `enrich_entry_prompt` merges the new answer into the existing bullets (additive - adds what's new/more precise, doesn't delete a correct point just because the new answer didn't repeat it), then `replace_entry()` overwrites that entry in place, same mechanism the revise flow already uses. A visible `st.info` announces when this happens so it's never a silent behavior switch.

**Critical dependency, don't break this:** the revise-flagged-answers flow (`replace_entry` call in the "Revise flagged answers" button) ALSO calls `upsert_index()` now, immediately after updating `entry["entry_text"]`. Without that, the index would still point at the pre-revise `entry_text`, `find_prior_entry`'s verbatim-match check would fail on the next attempt (the old text no longer exists in the file), and a later save with identical notes would silently fall through to creating a duplicate entry instead of enriching - defeating the whole feature. Every code path that changes what's saved for a given set of notes (fresh save, revise, enrich) must call `upsert_index()` so the index never goes stale.

**Known, accepted tradeoff:** matching is purely by exact notes text, with no time window or session concept. Pasting the identical notes weeks later as intentional spaced repetition will also trigger enrich-merge (not a fresh dated entry), because there's no way to distinguish "still the same sitting" from "revisiting this later on purpose" - text identity is the only signal. Don't add a time-based cutoff or an explicit "is this a continuation?" confirmation step unless Jason asks; he asked for this exact automatic behavior.

# Semantic (not just exact-text) duplicate detection (added 2026-09-05)

The exact-hash matching above only catches literally identical Section 1 notes. It missed a real case the same day: two entries ("BRD Purpose, Structure, and Executive Summary" and "Understanding BRD Structure and Purpose") that covered the same narrow topic but were written up with different wording in two separate sessions - the hash-index couldn't have caught this even in principle, and the older entry also predated the index existing at all. Fixed that specific duplicate by hand (merged manually, no API call - the overlap was easy to eyeball) and updated `.study_log_index.json` to match the merged text.

To catch this class going forward: `organize_entry_prompt` (`prompts.py`) now also receives every existing entry title in the log (`existing_titles()` - a plain regex over `**Title**` lines) and, in the SAME classification call (no added API cost on the normal path), returns a `duplicate_of_title` field - the exact existing title to merge into, or empty if genuinely new. If the model flags one, `find_entry(title)` (`app.py`) locates that entry's current text by scanning the log's actual sections/regex rather than depending on the hash index (so it works even for legacy entries the index never tracked), and the save routes through the same `enrich_entry_prompt` + `replace_entry()` path used by the exact-match case. This only costs the same extra enrich call the hash-match path already costs - it does NOT add a call on every save, only when a duplicate is actually flagged.

This is a judgment call by the LLM, softer than the exact-hash check, so the `st.info` banner explicitly names which existing entry it matched to, making an overreach (merging two things that aren't really the same) visible rather than silent. If `duplicate_of_title` names a title that isn't an exact match to anything in the log (model paraphrased instead of copying verbatim), `find_entry()` returns `None` and the code falls through to a normal fresh append - never a crash.

**Requested but explicitly deferred:** a separate text box per generated retrieval prompt (rather than one combined answer box), each with the same autosave-on-blur behavior. Jason flagged this as "build later," not now — don't build it unprompted; when he asks, note it changes `raw_summary`/`check_understanding_prompt`/`organize_entry_prompt` from taking one blob of text to a list of per-prompt answers, which touches more than just the UI layer.

# Source link as a reference for truth (added 2026-09-23)

Jason asked for an optional field to paste the link to the resource he's taking notes from, so the fact-check has a real reference instead of the model's memory alone. `src/orchestration/source.py::fetch_source()` fetches the page (requests + stdlib HTML parsing, no extra dependencies), strips nav/script/footer noise, and caps the text at 30k characters. `app.py::get_source()` caches the result per URL per session so the prompt step, the fact-check, and the revise step all reuse one fetch; a "Retry loading the link" button appears if a fetch fails (failures are cached too, so a dead link doesn't re-hit the network on every rerun). The URL is saved in the in-progress draft file like the other boxes.

The text is threaded into `retrieval_prompts_prompt`, `check_understanding_prompt`, and `revise_entry_prompt` (`source_text` param). With a source, the check treats it as ground truth: it flags contradictions and names what the source says, confirms supported claims, and does NOT call a claim wrong merely because the source doesn't cover it. The source is fenced in the prompt as data, never instructions (`SOURCE_RULES`), since it's untrusted fetched content. Verified live against a Wikipedia page: a false claim was flagged with the correction quoted from the source, true claims were confirmed.

**Honest limits, by design:** video links (YouTube etc.), PDFs, JavaScript-only pages, and pages behind a login or paywall can't be read. `fetch_source` returns a specific error for each instead of pretending, the UI says the check fell back to the AI's own knowledge, and the result heading says whether a source was actually used. Don't let the app label a check "against your source" when no text was loaded. Adding transcript or PDF support would mean a new dependency; don't do it unprompted.

# Explicit scope boundaries

- **No Google Docs live-sync, and this isn't a bug to fix.** Verified 2026-08-26: Drive read/create access actually works (the earlier "broken" memory note was stale), but the Drive MCP toolset has no content-update call — only file metadata (title/parent folder) can be changed on an existing file. There is no way to keep pushing new entries into the *same* Google Doc over time with the tools available. `study_log.md` is the real system of record; Jason copies sections into Google Docs himself if/when he wants them there too. If a "push a one-off snapshot to a new Drive file" convenience button is ever wanted, that's buildable in ~10 minutes, but it creates a new file each time (no update-in-place) — don't build it unless Jason explicitly asks, and don't confuse it with the live-sync he originally asked for.
- No live-transcription / meeting-note-taker feature. Out of scope for a study tool, and not to be added without a separate decision.
- Subjects are open-ended (classified freely by the LLM, reusing existing headers from the log when they fit) rather than a fixed list — this started as a fixed, single-subject list (`TOPIC_BUCKETS`) until the 2026-08-26 generalization; don't reintroduce a hardcoded list.
- Deliberately kept to one Streamlit page, four possible LLM calls (retrieval prompts, transcription, organize, quick-check), no persistence beyond the log file itself. Do not add multipage navigation, a database, or session-resume state unless Jason explicitly asks — this tool exists to protect study time, not to become its own project (see The Registrar's build history for what happens when a "rough draft" tool keeps growing).
- This is NOT an agent (confirmed with Jason 2026-08-26) — every LLM call is a single-shot, fixed-purpose call triggered by one button click, no tool use by the model, no autonomous multi-step chains. Don't describe it as agentic in any doc or conversation; that word is reserved for things like The Registrar's actual `web_search`/`web_fetch` tool-use loop.

# Project Structure

- `app.py` - the entire UI, single page
- `src/orchestration/client.py` - Anthropic API wrapper, copied from the AI Tutor project's already-debugged version (truncation-aware retry included from the start), plus a `transcribe()` method for image/PDF handwriting OCR
- `src/orchestration/prompts.py` - `retrieval_prompts_prompt`, `organize_entry_prompt` (subject/tag classification, no fixed lists), `check_understanding_prompt` (post-save correctness feedback), `revise_entry_prompt` (rewrites only flagged content), `transcribe_prompt`
- `study_log.md` - the actual reference content. This file has real value and should be kept/committed, unlike gitignored run artifacts in Jason's other projects.
